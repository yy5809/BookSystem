# 教材采购与库存管理系统 — 代码审计技能

## 一、审计概述

### 1.1 系统信息

- **系统名称**：教材采购与库存管理系统
- **技术栈**：RuoYi-Vue 3.9.0、SpringBoot 2.x、Vue2、ElementUI、MySQL、Redis
- **系统角色**：超级管理员、教师、库管员、供应商
- **核心业务**：教材采购（Excel导入）、入库管理、班级领书、个人领书、缺书管理、库存管理

### 1.2 审计目标

1. 确保业务逻辑与设计文档一致
2. 确保数据一致性和事务完整性
3. 确保权限控制和数据隔离
4. 发现安全漏洞（SQL注入、XSS、越权等）
5. 发现并发问题和性能隐患

### 1.3 审计范围

| 层次 | 审计内容 |
|------|---------|
| Controller层 | 参数校验、权限注解、接口安全 |
| Service层 | 业务逻辑、事务管理、并发控制 |
| Mapper/DAO层 | SQL安全、数据权限、N+1查询 |
| 前端Vue层 | XSS防护、权限控制、数据展示 |
| 配置层 | Redis配置、数据库配置、安全配置 |

## 二、审计检查清单

### 2.1 业务逻辑审计（最高优先级）

#### A. 采购管理审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| A1 | Excel导入不修改库存 | 导入采购单时，**绝对不能**修改教材库存表的stock字段。采购是计划行为，只有入库才加库存 | 🔴 严重 |
| A2 | Excel按列下标读取 | 必须硬编码列索引读取Excel，不能按表头名称匹配（防止用户修改表头导致数据错位） | 🔴 严重 |
| A3 | 单行校验失败不阻断 | 逐行try-catch，单行校验失败只标记该行，不影响其他行导入 | 🟡 高 |
| A4 | 防重复导入 | 使用文件MD5或批次号防止同一文件重复导入生成重复采购单 | 🟡 高 |
| A5 | ISBN系统存在性校验 | 导入时校验ISBN必须在教材信息表中存在，不存在则标记失败 | 🟡 高 |
| A6 | 学院/专业字典校验 | 学院和专业字段必须在数据字典中存在，使用枚举校验 | 🟡 高 |
| A7 | 采购数量范围校验 | 采购数量必须为正整数，范围1-9999 | 🟠 中 |
| A8 | 已入库采购单禁止编辑 | 状态为"已到货"或"已入库"的采购单，前端隐藏编辑/删除按钮，后端接口加状态校验 | 🔴 严重 |
| A9 | 采购单号生成规则 | 格式：`CG + yyyyMMddHHmmss + 3位序号`，需保证唯一性 | 🟡 高 |
| A10 | 缺书单自动关联 | 导入时自动关联同ISBN的未处理缺书单，标记为"已纳入采购" | 🟠 中 |

**审计方法：**
```
1. 找到 Excel 导入接口（通常在 PurchaseController 中）
2. 检查 Service 层是否有任何 stock 更新操作
3. 检查 Excel 解析是否使用固定列索引
4. 检查是否有 MD5/批次号去重逻辑
5. 检查编辑/删除接口是否有状态前置校验
```

#### B. 入库管理审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| B1 | 入库事务原子性 | 入库操作必须使用 `@Transactional`，确保：增加库存 + 生成流水 + 更新采购单状态 + 更新缺书单 + 发送通知 全部成功或全部回滚 | 🔴 严重 |
| B2 | 库存流水不可篡改 | 流水表（book_stock_flow）只能INSERT，不能UPDATE/DELETE，后端不暴露修改接口 | 🔴 严重 |
| B3 | 入库前库存快照 | 流水记录必须包含变动前库存（stock_before）和变动后库存（stock_after） | 🟡 高 |
| B4 | 采购单状态流转 | 入库后采购单状态必须变为"已入库"，不允许跳过"已到货"直接入库 | 🟡 高 |
| B5 | 缺书单状态同步 | 入库完成后，关联的缺书单状态应自动更新为"已完成" | 🟠 中 |
| B6 | 供应商通知 | 入库后自动发送进书通知给对应供应商 | 🟠 中 |

**审计方法：**
```
1. 找到入库确认接口
2. 检查方法是否有 @Transactional 注解
3. 检查事务内是否包含所有必要操作
4. 检查流水表是否有 UPDATE/DELETE 的 Mapper 方法
5. 检查库存更新是否使用 SET stock = stock + #{qty}（而非先查后改）
```

#### C. 班级领书管理审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| C1 | 领书通知发布校验 | 发布前必须校验所有教材库存充足，库存不足的教材不允许添加或提示差额 | 🔴 严重 |
| C2 | 领书单自动生成 | 发布通知时，系统必须为每个班级自动生成一张领书单 | 🟡 高 |
| C3 | 出库事务原子性 | 确认出库必须事务保证：扣减库存 + 生成流水 + 更新领书单状态 | 🔴 严重 |
| C4 | 分批出库支持 | 实发数量可小于应发数量，状态为"部分出库"；累计实发=应发时自动变为"已出库" | 🟡 高 |
| C5 | 并发出库防超卖 | 多人同时确认出库时，库存不能变为负数。必须使用乐观锁或数据库行锁 | 🔴 严重 |
| C6 | 领书通知状态流转 | 草稿→已发布→领取中→已完成，所有班级出库完成时自动变为"已完成" | 🟡 高 |
| C7 | 出库数量校验 | 实发数量不能超过应发数量，不能超过当前库存 | 🔴 严重 |

**审计方法：**
```
1. 找到出库确认接口
2. 检查是否有并发控制（乐观锁 version 字段 或 SELECT ... FOR UPDATE）
3. 检查库存扣减 SQL：UPDATE textbook SET stock = stock - #{qty} WHERE stock >= #{qty}
4. 检查分批出库逻辑：issued_qty 累加是否正确
5. 检查 @Transactional 注解
```

#### D. 个人领书管理审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| D1 | 审核前库存校验 | 审核通过前必须检查库存是否充足 | 🔴 严重 |
| D2 | 取消申请限制 | 只能取消"待审核"状态的申请，已审核的申请禁止取消 | 🟡 高 |
| D3 | 数据权限隔离 | 教师只能查看本人提交的领书申请记录 | 🔴 严重 |
| D4 | 出库扣库存 | 确认出库时必须扣减库存并生成流水 | 🔴 严重 |
| D5 | 审核通知 | 审核后自动通知教师结果（通过/驳回） | 🟠 中 |

#### E. 缺书管理审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| E1 | 缺书单按ISBN合并 | 同一ISBN多人登记时，需合并处理、累加数量，避免重复采购 | 🟡 高 |
| E2 | 一键转采购单 | 缺书单转采购单时，自动关联缺书单ID，标记为"已纳入采购" | 🟡 高 |
| E3 | 状态自动同步 | 采购单到货→缺书单"已到货"；入库完成→缺书单"已完成" | 🟡 高 |
| E4 | 缺书通知 | 教师/库管员登记缺书后，系统自动通知库管员 | 🟠 中 |

#### F. 库存管理审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| F1 | 禁止直接修改库存 | 后端**绝对不能**暴露直接修改库存数字的接口，库存只能通过入库/出库变更 | 🔴 严重 |
| F2 | 库存预警 | 库存 ≤ 预警阈值时前端标红提醒，后端提供预警查询接口 | 🟠 中 |
| F3 | 流水只读 | 库存流水表只能查看，不能修改或删除 | 🔴 严重 |

### 2.2 权限控制审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| P1 | 教师数据隔离 | 教师只能查看本人的领书申请，MyBatis SQL 必须加 `teacher_id = #{currentUserId}` 条件 | 🔴 严重 |
| P2 | 供应商数据隔离 | 供应商只能查看与自己相关的采购单，SQL 必须加 `supplier_id = #{currentSupplierId}` 条件 | 🔴 严重 |
| P3 | 教师教材只读 | 教师角色对教材信息只有查询权限，Controller/Service 不允许调用新增/编辑/删除方法 | 🟡 高 |
| P4 | 接口权限注解 | 每个接口必须有 `@PreAuthorize` 注解，确保角色权限正确 | 🔴 严重 |
| P5 | 前端路由守卫 | Vue 路由必须配置角色权限，未授权角色不能访问对应页面 | 🟡 高 |
| P6 | 按钮权限控制 | 前端按钮使用 `v-hasPermi` 指令控制显示/隐藏 | 🟡 高 |
| P7 | 越权访问防护 | 后端接口必须校验当前登录用户是否有权操作该数据（不能只靠前端隐藏） | 🔴 严重 |

**审计方法：**
```
1. 搜索所有 @RequestMapping/@GetMapping/@PostMapping 注解
2. 检查每个接口是否有 @PreAuthorize 或自定义权限注解
3. 检查 Mapper XML 中的数据权限 SQL 拼接
4. 检查前端 router/index.js 中的 meta.roles 配置
5. 测试：使用教师账号尝试访问库管员接口
```

### 2.3 安全漏洞审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| S1 | SQL注入 | 检查所有 MyBatis XML，禁止使用 `${}` 拼接用户输入，必须使用 `#{}` | 🔴 严重 |
| S2 | XSS攻击 | 前端使用 `v-html` 的地方必须对内容做转义，后端接口入参做HTML标签过滤 | 🔴 严重 |
| S3 | 文件上传安全 | Excel上传接口必须校验：文件扩展名（.xlsx/.xls）、文件大小（≤10MB）、文件内容（防止伪装） | 🔴 严重 |
| S4 | CSRF防护 | Spring Security 是否启用 CSRF，或使用 Token 验证 | 🟡 高 |
| S5 | 敏感信息泄露 | 接口返回不能包含密码、Token等敏感信息；日志不能打印用户密码 | 🟡 高 |
| S6 | 接口限流 | Excel导入、批量操作等接口应有频率限制，防止恶意调用 | 🟠 中 |
| S7 | ISBN格式校验 | 前后端都必须校验ISBN格式（10位/13位），防止非法输入 | 🟠 中 |

**审计方法：**
```
1. 全局搜索 MyBatis XML 中的 ${} 用法
2. 全局搜索前端代码中的 v-html 用法
3. 检查文件上传接口的校验逻辑
4. 检查 Spring Security 配置
5. 检查日志配置，确认不打印敏感信息
```

### 2.4 并发与性能审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| N1 | 并发出库防超卖 | 库存扣减必须使用乐观锁（version字段）或悲观锁（SELECT FOR UPDATE） | 🔴 严重 |
| N2 | 采购单号唯一性 | 高并发下采购单号生成不能重复，建议使用数据库序列或分布式ID | 🟡 高 |
| N3 | N+1查询 | 检查循环中是否有数据库查询，应使用批量查询替代 | 🟠 中 |
| N4 | 大事务优化 | Excel导入事务不应过长，考虑分批提交或异步处理 | 🟠 中 |
| N5 | 索引检查 | ISBN、采购单号、领书单号等高频查询字段必须有数据库索引 | 🟡 高 |

### 2.5 数据一致性审计

| # | 审计项 | 检查要点 | 风险等级 |
|---|--------|---------|---------|
| DC1 | 库存与流水一致 | 每次库存变动必须有对应的流水记录，数量必须匹配 | 🔴 严重 |
| DC2 | 采购单状态一致性 | 采购单状态必须按 待采购→采购中→已到货→已入库 顺序流转，不允许跳转 | 🟡 高 |
| DC3 | 领书单数量一致 | 领书单的应发数量 = 明细表各教材应发数量之和 | 🟡 高 |
| DC4 | 逻辑删除一致性 | 使用 del_flag 逻辑删除的表，所有查询都必须加 del_flag = '0' 条件 | 🟡 高 |
| DC5 | 操作日志完整性 | 关键操作（导入、入库、出库、审核）必须记录操作日志 | 🟠 中 |

## 三、审计流程

### 3.1 标准审计流程

```
第一步：环境准备
  ├─ 获取系统源代码（后端 + 前端）
  ├─ 获取数据库DDL脚本
  ├─ 获取系统设计文档
  └─ 确认审计范围和优先级

第二步：静态代码扫描
  ├─ 搜索 ${} 拼接（SQL注入风险）
  ├─ 搜索 v-html（XSS风险）
  ├─ 搜索 @Transactional（事务覆盖）
  ├─ 搜索 @PreAuthorize（权限覆盖）
  └─ 搜索直接 UPDATE stock（非法库存修改）

第三步：业务逻辑审计
  ├─ 按模块逐个审计（采购→入库→领书→缺书→库存）
  ├─ 对照设计文档检查每个流程的实现
  ├─ 检查状态流转的完整性
  └─ 检查事务边界是否正确

第四步：权限审计
  ├─ 检查所有接口的权限注解
  ├─ 检查数据权限SQL
  ├─ 检查前端路由和按钮权限
  └─ 尝试越权访问测试

第五步：并发与性能审计
  ├─ 检查库存操作的并发控制
  ├─ 检查索引使用情况
  ├─ 检查N+1查询
  └─ 检查大事务

第六步：输出审计报告
  ├─ 按风险等级分类（严重/高/中/低）
  ├─ 每个问题包含：问题描述、代码位置、修复建议
  └─ 提供修复优先级排序
```

## 四、关键数据模型参考

### 4.1 核心表清单

| 表名 | 说明 | 关键约束 |
|------|------|---------|
| book_notice | 领书通知表 | notice_no唯一 |
| book_claim_form | 领书单表 | form_no唯一，关联notice_id |
| book_claim_form_detail | 领书单明细表 | 关联form_id、textbook_id |

| textbook | 教材信息表 | ISBN唯一 |
| purchase_order | 采购主单表 | order_no唯一 |
| purchase_order_detail | 采购明细表 | 关联order_id、textbook_id |
| book_shortage | 缺书登记表 | 关联textbook_id |

### 4.2 状态枚举

```
采购单状态：0待采购 → 1采购中 → 2已到货 → 3已入库
领书通知状态：0草稿 → 1已发布 → 2领取中 → 3已完成
领书单状态：0待领取 → 1部分出库 → 2已出库
个人领书申请状态：0待审核 → 1已通过 → 2已驳回 → 3已出库
缺书单状态：0未处理 → 1已纳入采购 → 2已到货 → 3已完成
```

## 六、20个关键风险点速查

| # | 风险点 | 后果 | 审计关键词 |
|---|--------|------|-----------|
| 1 | 采购单来源于教务处Excel | 误以为手动创建为主 | Excel导入、PurchaseImport |
| 2 | 领书通知在入库之后发布 | 逻辑顺序错误 | NoticeService、入库后提示 |
| 3 | 领书通知仅系统内展示 | 误以为要推送消息 | NoticeController、无推送逻辑 |
| 4 | 班委纸质签名 | 误以为电子签名 | ClaimForm、receiver_name |
| 5 | 支持分批出库 | 50人班只来30人无法操作 | issued_qty < planned_qty |
| 6 | 库存只能通过入库/出库变更 | 直接改库存导致不一致 | 禁止 UPDATE stock |
| 7 | 出库/入库必须加事务 | 库存与流水不一致 | @Transactional |
| 8 | 导入不修改库存 | 采购阶段就改库存 | PurchaseImport 无 stock 更新 |
